## Subjects

- **none** (baseline): No gateway or checker: the calls go straight to the FHIR server and the agent's report is the only account of what was stored.
- **http-status** (observer): Trusts the status code: a 2xx answer means the call did what it asked (a Bundle, every entry), anything else did nothing. It reads nothing back and raises no flag.
- **deedglass** 0.1.0-dev (gateway): deedglass serve built from this commit. Every agent call goes through the Gate as its own action, to a fhir connector with default settings (if_match when_known), each write read back at the version the server reported (Checked, L1) and Proven (L2) from Medplum's change log, with meta.author checked against the agent's client. The policy is the healthcare-fhir pack's refusals with writes allowed at L1 (bench/cmd/fhir-bench/policy.yaml). A Bundle or a conditional update goes through a REST connector (the fhir connector takes one resource per call), which records the call (L0, Claimed).

## What each subject said

### `01-conditional-create-match` on medplum: A conditional create answers 200 and stores nothing

FHIR R4 conditional create: with one match, the server ignores the create and answers 200 OK with the existing resource. Medplum does exactly that.

- **none**: stored nothing; it says create 1 Observation. the agent reports: Charted the heart rate (74 beats/minute) as a new Observation.
- **http-status**: stored nothing; it says create 1 Observation. POST Observation: HTTP 200
- **deedglass**: stored nothing; it says nothing. action 1 (create): allow, execution succeeded, MISMATCH at L1 (fhir_conditional_matched)

### `02-conditional-update-creates` on medplum: A conditional update with no match creates a second Patient

FHIR R4 conditional update: with no match and no id in the body, the server creates the resource. Medplum documents the same: if no matching resource is found, one is created from the given data.

- **none**: stored create 1 Patient; it says update 1 Patient. the agent reports: Updated the phone number on the patient's existing record.
- **http-status**: stored create 1 Patient; it says update 1 Patient. PUT Patient?identifier=urn:example:fhir-bench:mrn|173a8b4f55eb-pl: HTTP 201
- **deedglass**: stored create 1 Patient; it says doesn't say. action 1 (step1): allow, execution succeeded, VERIFIED at L0

### `03-transaction-as-batch` on medplum: A transaction Bundle is applied in part

Medplum documents that without the transaction-bundles feature flag a transaction Bundle is processed as a batch, with no atomicity and no error or warning. FHIR R4 batch entries are processed independently.
