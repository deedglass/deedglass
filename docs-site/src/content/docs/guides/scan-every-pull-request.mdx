Get one comment on each pull request that changes agent config, in your own repos only.

**Before you start**

- A GitHub repository you own or administer.
- On a private repo, a Pro licence in the secret `DEEDGLASS_LICENCE`. Public repos need nothing.

## Why two workflows

A pull request from a fork must never get a write token next to its own code. So the scan runs with read-only rights and saves its report as an artifact, and a second workflow, started by the first one finishing, posts the comment. The second workflow never checks out the pull request's code. `pull_request_target` is never used: it runs with a write token in the base repository's context, which is how fork code gets one.

## 1. The scan

```yaml workflow title=".github/workflows/scan.yml"
name: deedglass scan
on:
  pull_request:
    paths:
      - ".mcp.json"
      - ".cursor/mcp.json"
      - ".vscode/mcp.json"
      - "**/claude_desktop_config.json"
      - "**/mcp_config.json"
      - "package.json"
      - "pyproject.toml"
      - "requirements*.txt"
      - "deedglass.yaml"
      - "policies/**"
permissions:
  contents: read
jobs:
  scan:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@<full-commit-sha> # v4
        with:
          persist-credentials: false
      - uses: deedglass/scan-action@<full-commit-sha> # v1
        with:
          licence: ${{ secrets.DEEDGLASS_LICENCE }} # private repos only; leave out on public repos
      - name: Save the PR number for the comment workflow
        env:
          PR_NUMBER: ${{ github.event.pull_request.number }}
        run: echo "$PR_NUMBER" > deedglass-scan/pr_number
      - uses: actions/upload-artifact@<full-commit-sha> # v4
        with:
          name: deedglass-scan
          path: deedglass-scan/
          retention-days: 7
```

## 2. The comment

```yaml workflow title=".github/workflows/comment.yml"
name: deedglass comment
on: # zizmor: ignore[dangerous-triggers] this job never checks out or runs the pull request's code; it reads the artifact as data
  workflow_run:
    workflows: ["deedglass scan"]
    types: [completed]
permissions: {}
jobs:
  comment:
    if: github.event.workflow_run.event == 'pull_request' && github.event.workflow_run.conclusion == 'success'
    runs-on: ubuntu-latest
    permissions:
      actions: read          # download the artifact from the scan run
      pull-requests: write   # one sticky comment, edited in place
    steps:
      # No actions/checkout here: this workflow never runs the PR's code.
      - uses: actions/download-artifact@<full-commit-sha> # v4
        with:
          name: deedglass-scan
          path: deedglass-scan/
          run-id: ${{ github.event.workflow_run.id }}
          github-token: ${{ github.token }}
      - uses: deedglass/scan-action/comment@<full-commit-sha> # v1
        with:
          report: deedglass-scan/
```

## What the comment step trusts

Nothing from the artifact is run. That is why the `on:` line tells zizmor, the workflow auditor, that this `workflow_run` trigger was reviewed: the job has no checkout and treats everything it downloads as data. It accepts a `pr_number` only when it matches `^[0-9]+$` and appears in `github.event.workflow_run.pull_requests`, and it renders the report as text. The comment is one sticky comment marked `<!-- deedglass-scan -->`, edited on each push. The SARIF file stays in the artifact.

## What it doesn't do

<Limits>
- It comments only in repos where you installed it, only when agent config or policy files change, and it never comments on anyone else's repo.
- It doesn't block a merge unless you make the scan job a required check.
- It never uses `pull_request_target`.
</Limits>
